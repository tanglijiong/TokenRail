# TokenRail 需求与范围

状态：首版设计基线，2026-09-13；尚未实现。

## 1. 从上下文提炼的目标

用户希望在银行金融职业方向上积累 Blockchain、EVM、Solidity 与智能合约能力，形成可运行、可解释、可用于面试的个人开源作品。现有 Java 和托管业务经验是业务基础；新项目的主要学习投入应在链上程序与传统系统的连接处。

TokenRail 的核心问题是：资金与证券在同一个可编程账本上表示后，如何安全交换，并将结果可靠地带回链下系统？成功标准包括实现闭环、可复现的异常证据，以及作者能自行解释关键原理。

需求来源是用户引用的《设计AI开源项目》对话，尤其最后一轮 TokenRail 规划。历史对话中的行业新闻不作为已核实事实沿用；技术依据见设计决策文档。

## 2. 使用者与业务模型

| 使用者 | 操作 | 能观察到的结果 |
|---|---|---|
| 学习者 / 开发者 | 部署、调用、故障注入、重放事件 | 状态、receipt、日志、余额、测试证据 |
| 模拟银行运营员 | 存款转换、发行及赎回跟踪 | 普通存款、转换中金额、代币负债支持金额 |
| 投资者 A / B | 发起、确认、授权、取消交易 | 成交条款、授权额度、交割结果 |
| 合规操作员 | 激活、到期、冻结测试身份 | 各类转移在执行时受到限制 |
| 结算 / 对账操作员 | 提交交割、检查异常、重建投影 | 可追溯的链上事实与链下差异 |

首版两个投资者均为同一家模拟存款发行行的客户。验证节点可以命名为 Bank A、Bank B、Issuer、Operator，但节点名称不意味着实现了两家银行存款之间的结算。

一份 DepositToken 代表该模拟发行行的一种 CNY 存款表示；一种 BondToken 代表一个债券系列。只使用合成标识 ABC2029，不将其标为真实 ISIN。

存款代币必须以链下模拟存款转换为来源，不能只做任意增发后声称实现银行存款。为避免重复计算，普通可用存款转换为代币负债支持金额；客户收到代币时不同时增加一份普通可用存款。赎回后才恢复普通可用存款。模型是教学账本，不是完整银行总账。

## 3. 版本范围

| 能力 | v0.1-core 内部里程碑 | v0.1 发布 |
|---|---|---|
| 身份准入、存款和债券代币、原子 DvP | 必须 | 必须 |
| 发行 / 赎回恢复、事件投影、同区块对账 | 必须 | 必须 |
| 四节点 Besu、Java API、集成测试 | 必须 | 必须 |
| 条件托管支付 PaymentEscrow | M6 已完成 | 必须 |
| 四页 Web 工作台、三场景脚本、视频 / GIF | 工作台与自动化场景已完成；录屏待 M7 | 必须 |
| ERC-3643、跨行存款 / 准备金模型 | 不做 | v0.2 候选，完成首版再选 |

原规划同时要求“四个合约”和独立的 Escrow 条件支付，二者不能完整兼容。本设计保留四个核心业务合约，再在 v0.1 发布前加入第五个 PaymentEscrow；不把托管状态强塞进 DvP。

不做交易所、订单簿、撮合、DeFi、NFT、真实资金、公链、跨链、CBDC、HSM/MPC、完整核心银行、付息兑付、Repo、ISO 20022、AI Agent。债券票息与到期日仅为元数据，不包含公司行动计算。交易总价由双方明确确认，不增加估值和计息引擎。

## 4. 产品流程

1. 初始化网络、发行行、投资者和允许的资产；身份登记仅存地址与合成机构标识。
2. 模拟银行转换 B 的存款并铸造代币；发行人向 A 配售模拟债券。
3. A 提交固定买方、券量、总价和截止时间的交割指令；B 在链上确认相同条款。
4. A 授权券，B 授权款；结算服务提交一次 DvP 调用。
5. 界面分别展示链上完成和链下同步状态；对账使用同一个区块的余额。
6. 独立测试资金不足、冻结、重复发送、事件消费中断及差异修复。

## 5. 最小界面

采用四个页面，中文解释与英文领域术语并列：

| 页面 | 必要内容 |
|---|---|
| 演示总览 | 选择固定场景、初始化状态、开始、当前网络与同步健康 |
| 资产与参与者 | 发行来源、身份状态、两种余额、mint / redeem 进度 |
| 结算详情 | 固定条款、双方确认、allowance、业务状态、交易历史与余额变化 |
| 对账与审计 | 区块高度和 hash、链上数、链下数、差值、重放记录 |

避免一键执行掩盖授权过程：演示台明确显示“正在以投资者 A 的本地测试身份确认”。私钥不进入浏览器。Receipt 等技术信息放在可展开的证据面板，主要流程使用“等待确认”“链上完成，持仓同步中”等可理解文案。

## 6. 完成标准

发布要求在干净环境中可复现三场景；有合约、Java、Besu 真实集成证据；能展示失败时券款余额不变、重放不重复记账、对账能发现并修复投影错误。README 不将模拟准入称为真实 KYC 服务，也不将本地实验称为已达到银行生产要求。
