# M2：同链原子 DvP

## 1. 条款确认与代币授权是两件事

ERC-20 allowance 只允许某个 spender 在额度内移动代币。它没有表达买卖对象、数量、总价、对手方或截止时间，因此不能作为对一笔交易的确认。

TokenRail 让卖方创建不可修改的指令，买方再把状态从 CREATED 推进到 READY。结算操作员只能执行已经 READY 的条款，没有代替买方确认或改变地址、数量、价格的入口。双方仍需分别授权 DvP 合约：卖方授权债券，买方授权现金。

## 2. READY 不等于锁定

首版采用非托管 pull 模型。创建和确认只记录意图，不把资产转进合约。READY 期间，余额、allowance、身份资格和冻结状态都可能变化，所以 execute 必须重新检查。

这种设计减少托管生命周期，但 READY 指令可能因余额不足、授权不足或资格变化而暂时无法成交。只要指令尚未到期或取消，修复条件后可以重试。链上不写 FAILED 状态，因为一次失败尝试没有改变业务指令本身。

## 3. 两条腿为何必须在一笔交易中

execute 先校验状态和条件，再暂置 SETTLED，随后依次调用债券和现金的 transferFrom。所有动作都在同一笔 EVM 交易的调用栈里。若第二条现金转移 revert，错误会继续向上传播，EVM 会撤销本次交易内已发生的状态变化，包括：

- 第一条债券转移及其 allowance 消耗；
- DvP 指令从 READY 到 SETTLED 的变化；
- 两种 Token 和 DvP 在失败路径上产生的事件。

失败交易仍进入区块并产生 `status=0x0` receipt；发送者 nonce 前进且支付 gas。这里的“余额不变”只描述业务资产状态，不代表交易从未发生。

如果把两条转移拆成两笔链上交易，即使 Java 使用数据库事务，也无法撤销已经确认的第一笔链上交易。应用只能设计补偿流程，不能获得同样的 EVM 原子性。

## 4. 时间、取消与暂停边界

执行要求 `block.timestamp < expiry`。因此 expiry 前一秒可执行，到达 expiry 后即使没人调用 expire 也不能执行；任何地址都可把仍处于 CREATED 或 READY 的过期指令终结为 EXPIRED。

到期前，卖方或买方均可取消 CREATED 或 READY 指令。暂停会阻止新建、确认和执行，但不会阻止双方退出未完成交易。取消、到期和结算都是终态，后续重放不会再次移动资产。

## 5. 本次证据与边界

单元测试覆盖正常成交、第二腿主动 revert、余额和 allowance 不足、未确认、越权、条款不可替换、重放、冻结、暂停、取消与到期边界。fuzz 使用 256 组随机合法金额；状态不变量验证供应量守恒、至少存在真实成功路径，以及终态后的非法动作不能成功。

真实 Anvil 实验广播了一笔第二腿必然失败的交易。receipt 为 `status=0x0` 且无日志，卖方债券、买方债券、债券 allowance、买方现金和 READY 状态均保持原值。完整结果见 [M2 本地证据](../evidence/m2-dvp-20260913/README.md)。

这些证据只覆盖单条 EVM 链上的技术原子性。银行账务、法律最终性、跨链交割、RPC 超时恢复和链下投影需要后续里程碑分别处理。
