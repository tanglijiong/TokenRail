## 2. 历史 M0 开发任务

按下列顺序完成 M0，不直接生成全部应用：

1. 检查本机 Java 21、Maven、Docker、Foundry 环境；记录当前可用版本。
2. 创建 Foundry 工程与固定依赖，锁 Solidity 编译器及 EVM target；提交依赖锁定方式。
3. 在 Anvil 演示 key → address → 签名 → 广播 → receipt；保存无敏感信息的实验记录。
4. 用最小状态合约观察成功状态变化与 revert 后的状态；该实验不算业务合约交付。
5. 建立合约构建测试 CI；将实验的五个关键概念写入学习记录。
6. 完成 M0 验收再进入 Registry 和 Token；Besu 正式配置在 M3 集成验证。

M7 已完成；后续按发布停止线冻结 v0.1.0 功能，仅处理实质缺陷与文档修正。

## 3. 每阶段工作方式

先读该阶段设计与一个官方概念说明，手动调用一个最小案例，再实现边界和错误路径，最后跑相关测试并留下自己的解释。使用编码助手时要求解释状态、授权和失败语义；合约关键测试由作者阅读理解，而不是仅接受“全绿”。

每个里程碑需留下：可运行变化、验收证据、一页学习记录、当前限制。只运行对当前改动有意义的验证；涉及链或账务时必须覆盖相应集成故障，不用 UI 截图代替。

## 4. 发布停止线

v0.1-core 是内部检查点，缺少条件支付与录屏时不能当成最终 v0.1 发布。正式 v0.1 完成后冻结功能，整理面试叙述，不为了增加技术名词继续堆功能。

v0.2 再从 ERC-3643 与跨行存款模型中选一个方向。后者先解释不同银行负债与最终结算资产，再决定技术实现，不能把两种 Token 按同一币种直接当成同一资产。
